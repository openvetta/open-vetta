06 · 装配

人设是编译输入，不是新引擎

选中「开发员」，或「开发团队里的开发员」。每次打开会话都重新解析，改了能力，重开会话即生效。

  1. 读档案 → 人格 addon + 能力白名单
  2. 若是团队成员 → 追加任务书
  3. 若是团队成员 → 注入团队工具，摘掉 spawn_agent
  4. 交给 RuntimeHost.agents["coding-agent"]
  5. 本 Turn 拿一份不可变 snapshot

08 · 何时用

团队是贵的，贵得有理由才开

值得组队

要第二个视角

工作分阶段：先取证、再实现、最后审查。作者不该审自己。同一批材料要多个角度再合并。

用普通会话

目标单一就别拆

一两轮能做完。你要边看边改、频繁介入细节。没有可并行或需要交接的部分。

09 · 可辩护的决策

介绍时经得起追问的六条

人设是 addon不替换基座 prompt，设计师和开发员不是两种引擎。
插件是供货方清单 1:1 维护。作者收得回，两台机器不会长歪。
角色槽位松耦合团队写 role: designer，不必绑死插件 id。
共享结论不共享过程独立视角来自上下文隔离。
任务书是增量同一人进两支队，人格跟着本体，只追加本队盯什么。
子代理工具被摘掉团队任务归属不能偷偷变成私有 spawn。
收束

我们没有做能任意互调的多智能体网。我们做的是：同一个可靠内核，加上可插拔人设，加上一条归属清晰的团队协议。

独立视角来自隔离，不是来自更多模型同时说话。

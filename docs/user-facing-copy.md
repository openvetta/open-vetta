# 面向用户的文案原则

> 本文记录 Vetta 桌面端（尤其是设置与能力扩展类 UI）在迭代中沉淀的文案与信息架构原则。  
> 读者：写 UI 文案的人、改设置页的 agent、做产品交互的人。  
> **不是** API 文档，也不是 i18n 工程规范（i18n 见 [ADR-0031](./adr/0031-desktop-i18n-i18next-semantic-keys-main-owned-language.md) 与 `packages/desktop-app` 的 AGENTS）。

---

## 1. 先认清用户是谁

目标用户**大致知道**产品名词（例如 MCP、模型、知识库），但通常：

- 不知道协议细节、传输类型、配置文件路径、包管理器命令；
- 不关心「怎么实现的」；
- **在意「这东西能帮我做什么」**、开/关有什么影响、下一步点哪里。

因此：

| 可以保留 | 不要默认甩给用户 |
|----------|------------------|
| 产品级名词：MCP、模型、知识库 | 实现级词：stdio、http transport、npx、spawn、mcp.json |
| 浅层动作：添加、关闭、删除 | 内部机制：懒加载、diff-reload、子进程 |
| 结果：对话里能用浏览器 | 手段：Playwright / 命令行参数 |

**用户懂名词 ≠ 用户懂实现。** 文案应假设「知道名字、不了解内核」。

---

## 2. 核心原则：说结果，不说实现

每一句用户可见文案，先问：

> 用户看完，能否判断「这对我有什么用」？  
> 若只能回答「系统是怎么干的」，就改。

### 2.1 能力描述写「能做什么」

**差：**

> 基于 Playwright 的浏览器自动化。通过 stdio 启动 `@playwright/mcp`。

**好：**

> 让 AI 打开网页、点击按钮、填写表单、截图并阅读页面内容，帮你完成浏览和简单网页操作。

句式优先：**主体（AI/你）+ 具体动作 + 场景收益**。少堆产品内部品牌与技术栈名。

### 2.2 页面说明写「用途 + 下一步」

**差：**

> 管理 MCP（模型上下文协议）集成的服务器配置。配置写入 `~/.vetta/agent/mcp.json`。

**好：**

> 管理 MCP，给 AI 增加额外能力，例如浏览网页、使用外部工具。添加后可在对话中直接使用。

需要路径、JSON、命令时，放进 **JSON / 高级 / 开发者** 路径，不要占主视图。

### 2.3 开关与状态用生活语言

| 技术说法 | 用户说法 |
|----------|----------|
| disabled | 已关闭 / 关闭 |
| enable server | 启用 |
| install（若实际只是写配置） | 添加 |
| config saved | 保存 / 已添加 |

避免把「写配置」说成「安装」——除非产品真有独立安装步骤。

---

## 3. 信息架构与文案一体

文案乱，常常是因为 **同一批东西用三种标签、三套列表** 同时讲。

### 3.1 用户心智优先于内部分类

内部可以有：内置预设 / 远程市场 / 用户手填。  
用户心智更接近：

1. **我现在有哪些**（已添加）  
2. **我还能加哪些**（发现）

商店式结构与此对齐：

- 上方：已添加（统一列表，来源用小标签区分即可）  
- 下方：发现（推荐 / 远程 / 手动 Tab）  
- **已添加的项不要在发现区再出现一遍**

### 3.2 标签用于辨认，不是科普

- 「推荐」：应用预置，可点添加  
- 不必在每条下再解释「配置由应用维护、写入本地文件、首次 npx…」

用户加完后，在「已添加」里用开关管理即可。

### 3.3 少写解释性副标题

默认不写：

- 「关闭开关即暂停，不会删除」  
- 「配置文件路径：…」  
- 「不可编辑」的长说明  

**控件本身应讲清行为**（开关 = 开/关，删除 = 去掉）。  
只有操作不可逆、易误解或合规要求时，才加一句。

多余标题（如列表上方再写「已添加」且与页面标题重复）会增加噪音；去掉后让列表直接承接页面主标题。

---

## 4. 产品名与营销腔

### 4.1 保留用户已认识的产品名

若用户已把设置入口认作 **MCP**，不要为了「口语化」改成完全陌生的「扩展能力」作侧栏名。

推荐：

- 侧栏 / 页标题：**MCP 管理**（名熟 + 动作清晰）  
- 正文说明：用「能力、对话里能用」解释 **MCP 能干什么**

### 4.2 避免工程师独白

少用：

- 「不会预先安装」「首次连接时 spawn」  
- 「与远程市场添加策略一致」  
- 「仅 UI 展示用 displayName」

这些写进 ADR / 注释 / CHANGELOG 即可，不进用户 UI。

---

## 5. 分层展示（主路径 vs 高级）

| 层级 | 给谁 | 可以出现什么 |
|------|------|----------------|
| 主路径（视图） | 大多数人 | 名称、能力说明、添加/开关/删除、推荐列表 |
| 表单基础项 | 手填用户 | 名称、命令、参数 或 URL |
| 高级折叠 | 少数人 | 环境变量、超时、调试、传输类型 |
| JSON 模式 | 极客 / 排障 | 完整配置、文件路径 |

原则：**默认界面零实现细节；实现细节可发现、不主动砸脸。**

列表行优先：

```
[图标] 名称  [标签]
       一两句「能做什么」
```

不要默认挂：

```
npx -y @playwright/mcp@latest
HTTP · https://...
stdio
```

---

## 6. 中英与语气

- 中文：短句、动词靠前、少从句套从句。  
- 英文：同样 outcome-first；不要把中文技术说明直译成协议说明书。  
- 统一走 i18n key；用户可见字符串不写死在组件里（desktop-app 已有约定）。  
- 空状态写 **下一步**：「还没有…，可在下方「发现」中选择。」而不是只写「暂无配置。」

---

## 7. 写作检查清单

发 PR / 改设置文案前自问：

1. **结果**：用户能否说出这功能对自己有什么用？  
2. **动作**：下一步该点什么是否清楚？  
3. **噪音**：有没有路径、命令、协议、包名可以下沉到高级区？  
4. **重复**：同一条目是否在多个区块重复出现？  
5. **名词**：产品名是否沿用用户已熟悉的说法？  
6. **真实性**：有没有把「写配置」说成「安装」、把「关闭」说成「卸载」？  
7. **必要解释**：这句删掉后，用户会不会严重误解？会 → 留；不会 → 删。

## 8. 反例与正例对照（摘自 MCP 设置迭代）

| 场景 | 避免 | 采用 |
|------|------|------|
| 页说明 | 管理 MCP 服务器配置文件 | 管理 MCP，给 AI 增加额外能力…添加后可在对话中使用 |
| 浏览器 MCP | Playwright / npx 说明 | 打开网页、点击、填表、截图、读页面 |
| 分区 | 推荐 + 远程 + 自定义三块平铺且重复 | 已添加统一列表 + 发现 Tab，发现区去重 |
| 副文案 | 「关闭开关即暂停，不会删除」 | 不写；开关语义自明 |
| 区块标题 | 页面已叫 MCP 管理，列表上再写「已添加」 | 可去掉重复标题，直接列表 |
| 侧栏名 | 改成纯「扩展能力」丢掉 MCP | **MCP 管理** |

---

## 9. 和代码的边界

- **用户文案**：i18n JSON、按钮 label、空状态、能力描述。  
- **开发者文案**：日志、CHANGELOG 技术段、ADR、代码注释——可以说实现。  
- Agent 改 UI 时：默认按本文写用户串；技术说明写进 CHANGELOG/注释，不要塞进 `t("…")` 的主路径文案。

---

## 10. MCP / 第三方连接的授权文案

用户最怕的不是「多填一个框」，而是**不知道去哪拿、要多久**。

| 优先级 | 策略 | 用户负担 |
|--------|------|----------|
| 1 | 浏览器登录（OAuth） | 最低 |
| 2 | 「去获取」链接 + 分步说明 + 粘贴 | 中 |
| 3 | 先添加、稍后填 | 可延后 |
| 4 | 对话里让 AI 带一步 | 辅助 |
| 5 | 只甩 env 名 | 禁止 |

实现约定（desktop MCP 推荐）：

- 推荐列表用标签区分：**即用 / 登录即可 / 需密钥**
- 弹窗标题用「连接××」，步骤口语化，按钮「去获取」打开官方发凭证页
- 必填密钥才阻断添加；否则可「先添加，稍后填写」
- 密钥只存本机的提示写一句即可

## 11. 一句话

> **用用户听得懂的产品词，讲清楚能做什么和怎么用；实现细节留给高级入口和文档。**

本文随产品继续迭代；若新场景与上述冲突，优先保证「结果优先、主路径安静」，再更新本节。

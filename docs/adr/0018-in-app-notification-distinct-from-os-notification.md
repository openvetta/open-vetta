# 站内信与系统通知并存为两套独立通知系统

## 背景

系统已有「系统通知」（ADR 无独立编号，见 CONTEXT.md「系统通知」）：desktop-main 经 **OS 原生通知中心**弹出横幅，由**本地 session 事件**（agent 完成 / 提问待确认）触发，不持久化、无应用内收件箱。

新需求要求 admin 对用户的订阅操作（移除 / 更改 / 重置额度）能「发送到用户的通知里」，并在 desktop 消息中心的「通知」(铃铛) Tab 内累积、离线上线后仍可见。desktop 的该 Tab 当前是空壳，后端无任何通知表。

## 决定

新增**站内信（in-app notification）**作为一套与系统通知**彼此独立**的通知系统：

- **站内信** = 服务端产生、持久化进 `notifications` 表、经 SSE 实时下发、在应用内铃铛 Tab 累积、带 per-user 已读状态的通用类型化消息（`type` 判别，首期消费者是订阅操作，未来事件复用同表与同套接口）。
- **系统通知** = OS 通知中心横幅，本地 session 事件触发，不持久化。

两者可叠加（一条站内信到达时也可顺带弹一次系统通知），但**存储、入口、触发源彼此独立**。

## 取舍

考虑过的替代：① 仅用瞬时 SSE toast（不持久化）——离线即丢失，不满足「进到通知里」；② 复用 OS 系统通知基础设施加一个 NotificationType——但它本质是本地 session 事件驱动、无应用内收件箱、服务端无法直接触发。两者都不能提供「服务端推送 + 应用内可回看」的语义，故新建持久化站内信。

代价：系统内并存两套通知概念，命名易混。已在 CONTEXT.md 用「站内信」「系统通知」两个术语显式消歧，约定**不要**把服务端推送的应用内消息叫「系统通知」。

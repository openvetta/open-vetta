# 工作空间归属改存 `~/.vetta`，由主进程持有

部分取代 ADR-0155 的存放决策：ADR-0155 把空间注册表与归属放在 Renderer 的 localStorage。

## 背景

空间记录的是「项目 X、会话 Y 属于哪个空间」，而项目注册表、会话文件、Team 归属目录都在 `~/.vetta`。把归属单独存在 Electron userData 里，它就和所指向的数据分属两个作用域：

- 共用 `~/.vetta` 的两个安装（例如 `dev:home` 与正式版）项目相同，分组却各不相同；
- 清理或重装 userData 后，项目还在，分组没了；
- ADR-0159 需要让主进程也能读到归属，只好再维护一份 Renderer 推送的镜像。

## 决策

1. **数据拆成两类。**
   - 共享的「空间数据」：空间列表（id、名称、图标、顺序、兄弟项目开关），以及项目和独立会话（含 Team 会话）的归属。存放在 `~/.vetta/spaces.v1.json`，主进程是唯一写入方。写入为原子写，写完广播给所有窗口。
   - 每个应用自己的「界面状态」：当前选中的空间、每个空间上次打开的位置。继续留在本地 localStorage。
2. **localStorage 保留为同形缓存，继续写全量。** 键与结构都不变（`vetta.desktop-spaces.v1`，`SpaceState`）。
   - 首帧仍然同步读它，侧栏不会先空再跳。
   - 主进程的数据一变化就回写到这里，降级到旧版本时仍能看到最新分组。
3. **启动握手由主进程裁决**（`sync`），Renderer 提交三样东西：本机来源 id（每个 userData 一个随机 id）、本地空间数据、本地数据是否在同步之外被改过。主进程按下列规则处理：
   - **文件不存在**：用本地数据建立文件，即首次升级的导入。
   - **这个来源从未导入过**：把本地数据**并集合并**进文件，然后记下这个来源。用于共用 `~/.vetta` 的多个安装，或者同一个 userData 切换到另一个 `~/.vetta`。
     - 空间按 id 取并集；
     - 同一个项目或会话在两边归属不同时，以文件里已有的为准；
     - 指向已不存在空间的归属会被丢弃。
   - **本地在同步之外被改过**：以本地为准，整份覆盖文件。本地被改过可能是因为降级到旧版本时改了分组，或者主进程暂时不可用时的修改。判定依据是本地数据和「上次成功同步时的内容」不一致。
   - **其他情况**：以文件为准。
4. **运行期**：Renderer 改动空间时把空间数据整份交给主进程保存，收到广播后再应用到本地。主进程监听文件变化，其他进程（另一个安装）写入后也会广播，各窗口实时跟进。并发写入以最后一次写入为准。
5. **主进程不可用时不阻塞界面**：Renderer 照常改本地缓存，之后重试。下次握手时会被判定为「本地在同步之外被改过」，自动补交。
6. ADR-0159 的镜像（`space-sibling-projects.v1.json` 与推送通道）随之删除，兄弟项目直接读取这份存储。镜像从未发版，不需要迁移。

## 后果

- 老用户升级后感知不到变化：首帧读的是同一份 localStorage，首次握手只是把它原样导入。不需要重新登录、不需要迁移配置。
- 共用 `~/.vetta` 的多个安装在各自首次启动后会合并成同一套分组，这是本决定的目的。
- 以后调整空间数据结构，只需要在主进程里按 `schemaVersion` 迁移这一个文件，Renderer 缓存跟着主进程走，不会再在两处各留一份历史格式。
- 降级之后改分组，再升级时以本地为准，可能覆盖期间另一个安装对同一文件的修改。这种情况罕见，作为已知取舍接受。
